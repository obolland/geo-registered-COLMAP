# Runtime rendering and headsets - what the runtime constrains the pipeline to output

Researched 2026-11-12. Labels: VERIFIED (read in the linked primary source), INFERRED (reasoning from verified facts), UNVERIFIED (plausible, no primary source found, or only a secondary/anecdotal source). Versions and dates are given per claim.

## 1 Summary - the 10 findings that matter most

1. **WebGL2 is the only WebXR path that ships to every target headset today.** WebGPU-inside-WebXR (`XRGPUBinding`) works on Apple Vision Pro Safari (PlayCanvas renders WebGPU XR on AVP since engine v2.19.0, 2026-05-28) but on Quest Browser it is still labelled experimental through 152.1 (2026-10-02), with composition layers behind `chrome://flags` "webxr experiments"; Chrome's status entry says "No active development" for desktop/Android. Design for WebGL2 on Quest now, WebGPU as an upgrade path. (VERIFIED, sources in section 2)
2. **Splat count budgets on Quest 3 are small: plan for 0.5-1M rendered splats per frame (both eyes), not 5M.** Spark's default LoD budget is 500K for Quest ("Oculus"), 750K for Vision Pro; its guide says Quest 3 "1 million splats or less". A native Unity renderer (SplatXR, UIST 2026) holds 72 fps only to 100K and averages 59 fps at 200K. (VERIFIED)
3. **Overdraw (fill rate), not splat count alone, is the dominant Quest cost.** PlayCanvas profiling on Quest 3 found peripheral overdraw dominant and added foveated contribution culling (v2.20.0). Big, soft, overlapping splats (sky, road surface, distant hedges) are the expensive ones. (VERIFIED)
4. **Both serious renderers do budgeted, streamed, hierarchical LOD; the pipeline must output an LOD hierarchy, not one flat splat file.** PlayCanvas: Streamed SOG (`lod-meta.json` + per-chunk SOG, binary spatial tree, global splat budget). Spark 2.x: `.RAD` LoD tree, paged over HTTP Range, shared 16M-splat page pool. (VERIFIED)
5. **Recommendation: PlayCanvas engine** (MIT, releases every 1-4 weeks, v2.24.1 on 2026-11-12) for its WebGPU compute GPU sort with stereo XR, foveated culling, global budget across many assets, WebGPU XR already working on AVP, and a WebGL2 CPU-sort fallback for Quest today. Spark (MIT, v2.4.0 2026-10-20) is the strong alternative but is WebGL2-only and fixed basic WebXR splat-size bugs only in Oct 2026. mkkellogg GaussianSplats3D is unmaintained (README says so; last release 2025-01). (VERIFIED facts, INFERRED recommendation)
6. **Coordinates must be tile-local.** Spark's default 16-byte encoding stores centres as float16 (0.1% relative precision: 1 unit steps at 1000 units); SPZ positions are 24-bit fixed point; SOG positions are 16-bit per axis over a per-file log range. A 20-80 km route in one coordinate frame will quantise badly. Each tile needs a local origin (metres, ENU-aligned) plus a double-precision tile-origin transform in a manifest; the runtime should use a floating origin near the rider. (VERIFIED encodings, INFERRED requirement)
7. **SOG is the most compact runtime format** (spec v3: WebP textures, 16-bit positions, codebook scales/SH, "15-20x smaller than PLY"; INFERRED roughly 12-17 bytes/splat with SH3, 6-10 with SH0). SPZ v4 (ZSTD, 24-bit positions, SH up to degree 4) is about 10x smaller than PLY and is the compression carried by glTF/3D Tiles. (VERIFIED ratios, INFERRED bytes/splat)
8. **KHR_gaussian_splatting is ratified** (registry update 2026-09-03; PlayCanvas loads it since v2.21.0, CesiumJS since 1.139). Its compression sub-extensions (SPZ_2, EGSC, L-GSC) are still open PRs. Use glTF as an interchange/archive option, not the runtime streaming format. (VERIFIED)
9. **Refresh rate and foveation are controllable from the page on Quest** (`supportedFrameRates`, `updateTargetFrameRate`, `fixedFoveation`). Quest Browser defaults to 72 Hz unless the app asks for more. The pipeline cannot change this, but it sets the splat budget: 90 Hz leaves about 20% less GPU time per frame than 72 Hz. (VERIFIED APIs, INFERRED arithmetic)
10. **Web Bluetooth is absent from Quest Browser** (forum reports, UNVERIFIED in Meta docs) and Safari (WebKit has never shipped it, UNVERIFIED here); desktop Chrome/Edge have it. The smart-trainer link likely needs a companion path (phone/PC bridge) on Quest and AVP. The trainer research covers this.

**Recommendation: PlayCanvas engine (code-first, not the Editor), with a one-week Quest 3 bake-off against Spark before committing.** (INFERRED)
- It is the only option that already runs splats through WebGPU XR (AVP today, Quest when Meta ships it) and falls back to WebGL2 on the same code, so the product gets the WebGPU upside without a rewrite. Spark would need a WebGPU port that is an open issue.
- GPU compute sort removes the CPU-sort latency that shows as popping when the head turns, which matters for sickness. On Quest today both engines are on the WebGL2 CPU/worker sort path, so the Quest-today advantage is unproven: that is what the bake-off measures.
- Global budget across many assets, distance-banded LOD and foveated culling map directly onto a long linear route split into tiles.
- Risk accepted: PlayCanvas's LOD API churned (error-based LOD added in 2.22 and removed in 2.23); pin engine versions and test upgrades.
- Spark's LoD tree (continuous, per-splat, foveated selection, 500K Quest default) is arguably the better LOD design; if the bake-off shows it clearly smoother on Quest, three.js + Spark is a defensible choice. The pipeline should stay format-neutral so the choice stays reversible (section 6).

Derived budget for this product (INFERRED):
- Frame time is 13.9 ms at 72 Hz, 11.1 ms at 90 Hz. Start Quest 3 at 72 Hz with 0.5-0.8M rendered splats, fixed foveation on, framebuffer scale below 1 if needed, then try 90 Hz.
- The rider looks mostly forward down a road: forward-cone LOD (Spark foveated LoD, PlayCanvas foveated culling) fits well, and behind-the-rider detail can be very coarse.
- Overdraw: sky, road and large soft splats dominate. Pipeline should cap splat scale and prune low-opacity large splats, and put sky in a separate environment layer or skybox.
- Streaming rate at 18 m/s: if LOD0 holds about 10K splats per metre of route corridor, LOD0 alone needs about 180K splats/s, about 2.7 MB/s (22 Mbit/s) at 15 B/splat. Lower SH (degree 0-1 for mid/far LODs) and lower density cut this. Measure real density from the 1 km MVP.

## 6 Implications for the pipeline outputs

1. **Master + derived outputs.** Keep a lossless master per tile (3DGS PLY or KHR_gaussian_splatting GLB, float32, full SH) and generate runtime packages from it: Streamed SOG (`splat-transform`) for PlayCanvas and RAD (`build-lod --quality --rad-chunked`) for Spark. Both tools read PLY. (INFERRED from VERIFIED tool inputs)
2. **Tiling along the route.** Cut the route into contiguous corridor tiles (start at 100-250 m of route length, width = road corridor plus a visual margin), each with its own local origin. Each splat belongs to exactly one tile (crop by ownership after training with overlap) so no duplicated splats double up in the global sort. Both engines sort all loaded assets together (PlayCanvas global budget "accounts for all GSplat assets"; Spark "composite LoD worlds"), so seams blend if there is no duplication. (VERIFIED engine behaviour, INFERRED tiling)
3. **LOD levels per tile.** Produce LOD0 (full) plus 3-4 coarser levels (for example 50%, 25%, 10%, 3%) from the trained model, preferring training-time or quality-aware simplification over uniform decimation; use `--decimate-adaptive` for mixed scale content. Far levels can drop SH to degree 0. (VERIFIED options, INFERRED ratios)
4. **Environment layer.** Export far field / sky separately as an environment splat (`--tag-lod -1`) or skybox, loaded once per segment. (VERIFIED feature)
5. **Coordinate conventions.** Pipeline frame: ENU metres, right-handed, geo-registered via RTK. Per tile: local origin = tile centre in ENU (float64 in the manifest), splat positions relative to it so all coordinates are within a few hundred metres (fits float16/SPZ/SOG precision). Record the axis convention explicitly: SOG stores the 3DGS PLY frame and PlayCanvas applies a 180 degree rotation about z (VERIFIED, SOG spec section 2); SPZ defaults to RUB with a declared source frame (VERIFIED); glTF is y-up right-handed. Do one conversion ENU (z-up) -> runtime y-up at the tile transform, not in the data. (INFERRED)
6. **Manifest.** One JSON route manifest: route polyline (the ridden line, with distance along route), tiles ordered by route distance with ENU origin, bounds, per-format URLs, splat counts per LOD, SH degree, training flags (antialiased / mip-splatting: SOG `model: "antialiased"`, SPZ flag 0x1), and the ENU origin lat/lon/h.
